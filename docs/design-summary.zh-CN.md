# 代码设计摘要

当前交付是可实施的工程设计、接口契约和可运行的契约测试，还不是可使用的扑克 App。

## 技术方向

- Tauri 2 桌面壳，React/TypeScript 界面，默认英文，可切换中文。
- Rust 负责扑克规则、应用流程、训练状态与本地数据访问。
- 求解器运行在独立进程，使用可替换的适配器；先验证固定版本的 postflop-solver，TexasSolver 作为比较候选。
- SQLite 保存场景、任务和训练记录；大型策略与 EV 数据放在有索引、可按需读取的文件中。
- 训练读取已验证的完整预计算结果，不能在用户点击动作后偷偷启动求解。

详细职责与计划目录见 [架构设计](architecture.md)。这些目录在对应功能实现时创建，不预先堆积空模块。

## 已定义清楚的关键语义

1. 对手倾向先编译成完整、可检查的固定策略，再计算针对性打法；没修改的部分沿用基线。
2. 偏移程度首先采用策略概率混合，并重新计算该混合策略的 EV；不能直接对两份 EV 做线性插值。
3. 自动尺寸基于共同参考树比较，区分求解误差、尺寸简化损失和搜索是否充分。
4. 固定 flop 训练必须覆盖提供给用户的所有动作，以及对应合法 turn/river；只有根节点解不够。
5. 发牌必须考虑双方手牌之间的冲突；分别抽样后只重抽对手会造成偏差。
6. 保存完成、分支齐全、达到精度目标是三个独立状态。

公式、边界和比较方式见 [领域与算法语义](domain-and-math.md)。

## 引擎调查中的实际发现

候选 Rust 引擎已有部分所需接口，但上游暂停开发，必须固定版本并保留可维护的补丁。
其现有全深度结果序列化并不保存全部优化状态，不能直接宣称支持关机后精确续算。
手工锁定某个花色的策略还可能破坏引擎原来的花色对称性，需要专门验证或修改。

这些都是接入前要解决的具体项目，见 [引擎调查](solver-evaluation.md)。目前没有实测提速结论，也没有导入第三方代码或翻前数据。

## 实施顺序

| 阶段 | 可验收成果 |
| --- | --- |
| M0 | 最小原生引擎验证：正确性、对手锁定、真实断点、完整结果导出、内存测量 |
| M1 | 可保存与重开的场景研究工具，范围编辑、求解与分析 |
| M2 | 首个可用版本：固定 flop、预设对手、自动尺寸、连续训练、整手复盘与错题 |
| M3 | 深入尺寸搜索、多 flop / 后续牌聚合分析 |
| M4 | 翻前求解分阶段扩展，以及有基准证据的底层优化 |

8GB 首先保证读取已有结果进行训练；能够本地求解多大的树，以 M0 测量为准。
首版不依赖完整 6-max 翻前求解，也不把预设范围包装成自行求解的结果。

详细验收见 [实施计划](implementation-plan.md) 和 [验证方案](validation.md)。未来 AI 接手先读 [handoff](handoff.md) 与仓库 AGENTS.md。
